# 0001. engsys core는 POSIX sh로 두고 개발 도구만 python3를 쓴다

## 맥락

`bin/engsys`는 850줄 규모의 POSIX sh이고 YAML을 `sed`·`awk`로 읽는다. 이 파서는 engsys가
직접 쓴 형식만 해석할 수 있어서 중첩 계약이 늘어나면 한계가 온다. 반대로 프로젝트에
dependency를 설치하지 않는다는 것은 v0.1의 핵심 약속이다. 프로젝트가 표준을 채택하는 비용이
곧 표준이 실패하는 이유가 되기 때문이다.

두 요구가 충돌하는 지점은 "누가 실행하는가"였다. 프로젝트 개발자와 CI가 매번 실행하는 명령과,
시스템 레포를 고치는 사람만 실행하는 명령은 같은 제약을 가질 이유가 없다.

## 결정

실행 주체를 기준으로 경계를 나눈다.

- `bin/engsys`는 dependency 없는 POSIX sh를 유지한다. 프로젝트와 CI는 이것만 실행한다.
- `tools/*`는 시스템 레포 개발용이며 python3 표준 라이브러리를 쓴다. 프로젝트는 실행하지 않는다.
- 따라서 python3는 이 레포에 기여할 때의 전제이지, 표준을 채택하는 프로젝트의 전제가 아니다.

## 대안

- **전부 sh로 유지**: schema 검증과 카탈로그 생성을 awk로 구현해야 한다. 읽기 어렵고,
  검증기가 조용히 틀리면 검사 자체가 무의미해진다.
- **core를 python이나 Go로 재작성**: 파싱은 편해지지만 프로젝트가 runtime이나 binary 배포를
  떠안는다. v0.1이 검증하려는 "채택 비용 0" 가설을 스스로 깨뜨린다.

## 결과

- sh 파서의 한계는 남는다. 계약이 3단계 이상 중첩되거나 프로젝트가 계약을 손으로 크게
  고치기 시작하면 이 결정을 다시 검토한다.
- 그 한계를 조용히 넘기지 않도록, 계약 형식은 [ADR 0002](0002-contract-schema-is-canonical.md)의
  schema 검사가 test에서 잡는다.
- 시스템 레포의 test 실행에는 python3가 필요하다. README에 전제로 적는다.
