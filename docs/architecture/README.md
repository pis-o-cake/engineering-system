# Current architecture

This document describes **only how the system is built today**. The judgments made at design time
are in [design](../design), and the reasons for later changes are in [ADR](../adr).

Facts that can be derived deterministically from declarations, such as the lists and versions of
packages, skills and hooks, are not copied here. The [system catalog](../generated/system-catalog.md)
is generated by `tools/generate-catalog.py`, and `engsys verify` checks that it is up to date.

## Structure summary

The system has three layers. `packages/*` holds the source of truth for policies and for Claude
Code skills and hooks, `profiles/*` declares combinations of them, and an adopting project declares
its contract with `.engsys/project.yaml` and `.engsys/lock.yaml`. Beyond that, the system manages
project-owned hook copies, review receipts and similar files. Policy files are not copied into the
project.

The only command a project runs is `bin/engsys`. Because the lock pins which packages at which
revision are used, pulling the system repository does not change an existing project's combination
of skills and hooks.

## Components

- `bin/engsys` — the single entry point a project runs. It is POSIX sh with no dependencies.
  Only `setup` is interactive; everything else stays non-interactive so CI and scripts can call it.
  It handles contract generation (`init`), checks (`check`), diagnosis (`doctor`), project
  verification (`verify`), document structure checks (`docs`), document review (`review`), lock
  changes (`upgrade`) and launching Claude Code (`claude`).
- `install.sh` — developer activation. It changes only one line in the shell profile and this
  clone's `core.hooksPath`. It does not write to projects
  ([ADR 0007](../adr/0007-one-command-activation-and-main-as-release-channel.md)).
- `lib/plugin-runtime.sh` — the cache for the lock revision and assembly of the Claude plugin view.
- `lib/adoption.sh` — hook copy diagnosis and update, guided setup, doctor.
- `lib/generated-documents.awk` — the core parser that reads `documentation.generated` entry by
  entry. The order of `output` and `command` is free; missing, duplicate and unsupported syntax is
  treated as an error.
- `packages/*` — the source of truth for policies and for Claude Code skills and hooks. Not copied
  into projects. `docs-gov` holds document types and editorial review; `vcs-gov` holds the commit
  and MR conventions.
- `templates/project/*` — seeds that a project copies and owns. They are the Claude route rule and
  Git hooks, and once copied they are the project's files. The standard does not overwrite them;
  `engsys hooks status` only reports differences.
- `profiles/*` — package combination declarations.
- `schemas/*` — the source of truth for the project contract and lock formats.
- `tools/*` — development tools for the system repository (python3). Projects do not run them.

## Flows and execution paths

```text
engsys claude
  → select a clean worktree at the lock revision
  → build a plugin view with only the lock's packages (developer's local cache)
  → export ENGSYS_PLUGIN_ROOT, then run claude --plugin-dir from the project root
```

```text
engsys <check|sync|verify|docs|review|vcs> --project P
  → if P's lock revision differs from this checkout's commit, or the checkout has uncommitted changes,
      obtain a clean worktree at that revision and hand execution to its bin/engsys
  → fail if the locked revision cannot be prepared or the cache has been modified
  → init, upgrade, doctor and claude are not handed over
  → the system's own repository and an explicit ENGSYS_USE_CHECKOUT=1 run the code under development
```

```text
engsys verify --revision <commit>
  → assert that the working tree matches that commit (if not, print what differs and stop)
  → run the verify path below, then print the judged commit and the standard's revision
```

```text
engsys verify
  → engsys check (adapter and lock structure check)
  → commands.verify (native verification declared by the project)
  → documentation.generated[].command (whether generated documents are up to date)
```

Both commands can declare variants with a `-macos`, `-linux` or `-windows` suffix. engsys detects
the platform with `uname` and runs the variant if one exists, otherwise the base declaration. The
key it ran is printed in the output. A suffix that is not one of these never runs on any platform,
so `engsys check` rejects it
([ADR 0020](../adr/0020-platform-splits-belong-to-the-project.md)).

`engsys upgrade --apply` runs the verify path above with the new lock. On success it keeps the new
lock; on failure or interruption it restores the previous lock. Project files changed by a native
command are that command's responsibility and are not restored with the lock.

## Enforcement points

| Target | Claude assist path | Native gate |
|---|---|---|
| Direct edits to generated documents | Blocked in `PreToolUse` | `engsys verify` compares against the generator output |
| Contract format | None | `engsys check` checks top-level keys, required entries and that declared blocks were read. Full format: `tools/validate-contract.py` |
| Catalog copy consistency | None | `tools/check-consistency.py` |
| This repository's historical metadata and local links | Review guidance in the lifecycle skill | `tools/check-documentation.py` |
| Commit messages | The `write-commit` skill reads the contract and project declarations | The project's `commit-msg` hook runs `engsys vcs check-message` |
| Branch names | The `write-commit` skill asks `engsys vcs base-branch` for the branch base | The push gate runs `engsys vcs check-branch` only when the project declares `vcs.branch.naming` |
| Branch settings | None | If a `vcs` declaration exists, `engsys verify` runs `engsys vcs check-settings` |
| Document types and required structure | The `write-document` skill reads the type and contract before writing, and `PostToolUse` checks the one document just written and returns the result to the session | `engsys docs check` checks the declared type, metadata, sections and evidence paths |
| Editorial review of authored documents | Individual review with the `review-document` skill | `engsys review check` compares each document's review receipt with its body hash |
| Self lock freshness | None | Tests compare the lock revision with HEAD's `packages`, `bin` and `lib` trees |

Local hooks can be bypassed by people, so they are not the source of truth. The native gate checks
the same rules again. There is no server CI yet; enforcement before push is handled by
`.githooks/pre-push` (activated once with `git config core.hooksPath .githooks`).

The distributed hook fails even when the launcher is missing, and the hook for the system's own
repository also checks, for each pushed ref, the pushed content against the working tree with
`verify --revision`. It does not let an unchecked ref through with only a warning
([ADR 0019](../adr/0019-verification-fails-when-it-cannot-run.md)). Because there is no server
check, this pass is a result obtained in the pushing developer's environment.

The historical check reads the lifecycle paths in `.engsys/project.yaml` and the required metadata
and status lists in the docs-gov policy. It is wired into `tests/test-all.sh`, so it also runs in
this repository's `engsys verify`. It does not check whether past bodies match current code.
External URLs and heading fragments are also out of scope. This python tool is the system
repository's native check; adopting projects declare their own native document checks.

## Document type structure checks

`packages/docs-gov/document-types.yaml` is the source of truth for each type's readers, question,
required metadata and required sections. In `documentation.authoring` of `.engsys/project.yaml`, a
project assigns types to paths and declares paths excluded from checks (`exempt`) and paths whose
section checks are deferred (`deferred`).

For each assigned document, `engsys docs check` checks that the declared type matches the
assignment, that the status is in the type's vocabulary, that required metadata is filled in, that
evidence paths referenced by the metadata exist, that there is an introductory paragraph before the
first section, and that the required sections are present. For records in the type's
`frozen-status`, only the presence of sections is checked, not their order. HTML declares the same
metadata with `<meta name="doc-*">`.

The check runs at three points. Right after a document is written, the `PostToolUse` hook looks at
**only that one document** with `--path`, and on failure exits with code 2 so the result reaches
Claude inside the session. When a session opens, the `SessionStart` hook only counts documents
without a review receipt and does not recheck structure. Finally, `engsys verify` and the push gate
check everything. A `Stop` hook that validates everything on every turn is not used
([ADR 0009](../adr/0009-document-structure-feedback-at-write-time.md)).

This check judges structure only. `validate-document.awk` judges one document's metadata and
sections in a single pass, and the shell confirms paths and that referenced files actually exist.
Whether the wording is appropriate and the evidence sufficient is judged by the editorial review
below.

## Per-document editorial review

`packages/docs-gov/editorial.md` holds the editorial criteria for report, design and operations
documents according to their readers and purpose. The reviewer reads the whole document, edits it,
and then rereads the final version. `engsys review record` stores one document's hash and review
content in `.engsys/reviews/<document-path>.review`.

`engsys review check` reads the scope from `documentation.review.scopes` in the contract and
compares review receipts for the Markdown and HTML files in that scope, excluding generated
documents. New documents and documents changed after review fail. With `--revision <commit>`, the
scope, the list of generated documents and the bodies are all read from that commit, so later edits
in the working tree cannot stand in for the review of the documents being pushed.
This check does not score style automatically or prove that the document was actually read.

## Constraints and sources

- Commands that projects run use only POSIX sh with no dependencies. The `tools/*` that use python3
  are for system repository contributors only
  ([ADR 0001](../adr/0001-posix-sh-core-with-python-tooling.md)).
- The source of truth for the contract format is `schemas/*.json`; `engsys check` is an
  approximation. To change the format, change the schema first
  ([ADR 0002](../adr/0002-contract-schema-is-canonical.md)).
- Skills reach the plugin only through `ENGSYS_PLUGIN_ROOT`. `CLAUDE_PLUGIN_ROOT` is for hooks only
  ([ADR 0003](../adr/0003-skill-uses-launcher-environment.md)).
- This repository is the first pilot of its own standard, so a change to the standard breaks this
  repository's contract and documents first
  ([ADR 0004](../adr/0004-self-hosted-first-pilot.md)).
- The existence of a review receipt does not prove the quality of the writing or approval
  ([ADR 0005](../adr/0005-individual-document-editorial-review.md)).
- The document type contract enforces structure only. Type-specific rules are not copied into
  projects ([ADR 0006](../adr/0006-document-type-contract-in-posix-sh.md)).
- The release channel is `origin/main`, and the lock records the revision of the checkout that ran
  it. `doctor` only diagnoses and does not fix
  ([ADR 0007](../adr/0007-one-command-activation-and-main-as-release-channel.md)).
- `init --detect` fills in only declarations that are not set, and does not assign a type to paths
  that already contain documents
  ([ADR 0008](../adr/0008-init-detects-declarations-and-seeds-the-project-gate.md)).
- The structure check runs per document at write time and Claude receives the result. Editorial
  review is not moved there
  ([ADR 0009](../adr/0009-document-structure-feedback-at-write-time.md)).
- `SessionStart` only counts the review backlog. Running the full structure check every session was
  not worth it ([ADR 0010](../adr/0010-session-start-counts-review-backlog-only.md)).
- The push gate judges the commit being pushed. If the check target differs from that commit, it
  stops ([ADR 0013](../adr/0013-the-push-gate-judges-the-commit-it-sends.md)).
- Project commands run at the revision that project has locked. The checkout of the developer who
  runs them does not change the verdict
  ([ADR 0012](../adr/0012-project-commands-run-at-the-locked-revision.md)).
- A check that could not run is treated as a failure. A missing launcher or a locked revision that
  cannot be prepared is not passed with a warning
  ([ADR 0019](../adr/0019-verification-fails-when-it-cannot-run.md)).
- The project declares platform branches of native commands; the tool only chooses among them
  ([ADR 0020](../adr/0020-platform-splits-belong-to-the-project.md)).
- A document scaffold fills in only the form. Empty sections are caught by the structure check
  ([ADR 0016](../adr/0016-a-scaffold-fills-the-form-not-the-writing.md)).
- Hooks copied by a project are diagnosed, not overwritten. Two hashes are recorded: the template
  hash and the copy hash
  ([ADR 0015](../adr/0015-hook-copies-are-diagnosed-not-overwritten.md)).
- Adoption proceeds with `setup` confirming at each step. Before changing files it shows what it
  will change ([ADR 0018](../adr/0018-adoption-is-a-guided-sequence.md)).
- The standard holds no branch names. If none are declared, the tool does not answer
  ([ADR 0017](../adr/0017-the-standard-holds-no-branch-names.md)).
- The branch model defines only roles and promotion direction, and the project declares the names.
  Tools read that declaration and do not hardcode names
  ([ADR 0014](../adr/0014-projects-name-their-branches.md)).
- `vcs-gov` owns the commit and MR conventions, and the project declares only values. Commits are
  also created outside sessions, so enforcement is handled by native git hooks
  ([ADR 0011](../adr/0011-vcs-gov-owns-the-commit-and-merge-request-contract.md)).
